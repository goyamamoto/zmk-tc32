# zmk-tc32

ZMK for keyboards on Telink's TC32 chips (the TLSR8278), built on [zephyr-tc32](https://github.com/goyamamoto/zephyr-tc32), the Zephyr with the TC32 port. It is upstream [ZMK](https://github.com/zmkfirmware/zmk) `main` (`9ebbeff`) with the changes below and a Zephyr module for the TLSR8278 in `tc32/` ([tc32/README.md](tc32/README.md)): firmware updates over USB with the keyboards' original update protocol, two firmware slots with a guarded way back, an own BLE stack and the 2.4G link to the keyboards' dongle, backlights, a status display, ZMK Studio, US-JIS. The keyboards it builds for, their boards and keymaps are in [tc32-keyboards](https://github.com/goyamamoto/tc32-keyboards).

**At your own risk.** Firmware built from this repository replaces the keyboard maker's firmware, and `tc32/scripts/telink_ota.py` installs it. Installing it, using it or going back from it can make the keyboard unusable, lose its settings and pairings, or end the maker's warranty. It comes with no warranty of any kind (see [Licence](#licence)) and with no support: nobody, neither the authors nor the keyboard makers, Telink, the ZMK or the Zephyr projects, can help you or takes any responsibility for what happens to your keyboard, your computer or your data. The way back to the original firmware worked on the keyboards it was tried on; that is not a promise that it will work on yours. If you are not prepared to lose the keyboard, do not install it.

Besides on those keyboards, the images run in the TC32 emulator of [tc32-devtools](https://github.com/goyamamoto/tc32-devtools), which also holds the compiler tools the build uses.

## Where things are

| Path | What |
|---|---|
| `app/`, `docs/`, ... | ZMK as upstream, with the changes below |
| `app/west.yml` | West manifest: Zephyr is zephyr-tc32, at a pinned commit |
| `tc32/` | The TLSR8278 module (the boards are in [tc32-keyboards](https://github.com/goyamamoto/tc32-keyboards), a west manifest repository that imports this one): firmware slots, updates over USB, the boot guard, the USB device driver, USB suspend, the knob driver, the own BLE stack ([tc32/README.md](tc32/README.md)) |
| `tc32/compat/` | What ZMK main needs on Zephyr 4.4 ([below](#what-this-fork-changes-in-zmk)) |
| `tc32/scripts/build.sh` | Builds a profile ([Build](#build)) |
| `tc32/tests/` | The tests ([Tests](#tests)) |

The keyboards' USB device driver is here: `tc32/drivers/usb/device/usb_dc_b87.c` (`USB_DC_TELINK_B87`, built into Zephyr's library of legacy device controller drivers), for Zephyr's legacy USB device stack. zephyr-tc32 has a driver for the new device stack (`device_next`) only, and that stack does not fit these keyboards: for their USB functions (the keyboard, the update receiver's HID interface, CDC ACM for ZMK Studio) it takes about 16 KB more flash and 1.9 KB more RAM than the legacy stack, more than the 128 KB image slot and the 32 KB of SRAM leave.

## What this fork changes in ZMK

ZMK main expects zmkfirmware/zephyr 4.1; zephyr-tc32 is Zephyr v4.5.0-rc1 with the TC32 port. The changes below came with Zephyr 4.4 and still apply.

| Problem | Change | Kind |
|---|---|---|
| Zephyr 4.4's `board.yml` schema requires `full_name` | Added to ZMK's 21 `board.yml` files | Zephyr 4.4 |
| Zephyr 4.4's `sensor.h` asserts that a sensor device's API is in the `DEVICE_API(sensor, ...)` section; ZMK's sensor drivers (`ec11`, `encoder_mock`, `battery_*`, `max17048`) declare a plain `const struct sensor_driver_api` | Declared with `DEVICE_API(sensor, ...)`. Found by ZMK's encoder tests ([Tests](#tests)) | Zephyr 4.4 |
| The kscan API (`zephyr/drivers/kscan.h`, `KSCAN`, `drivers__kscan`, DT base binding `kscan.yaml`) was removed; ZMK's matrix drivers use it | `tc32/compat` restores the 4.1 header and binding (Apache-2.0), the Kconfig symbols and the library. It must come before ZMK's `app/module` in the module list | Zephyr 4.4 |
| `BT_CONN_TX_MAX`, set by ZMK Studio's BLE transport, no longer exists | `tc32/compat` gives it a type | Zephyr 4.4 |
| ZMK includes `<syscalls/...>` | `tc32/compat/zephyr44.conf` (`CONFIG_LEGACY_GENERATED_INCLUDE_PATH=y`, `CONFIG_WARN_DEPRECATED=n`), in every build | Zephyr 4.4 (deprecated path) |
| ZMK's Kconfig sets LVGL and Nordic HAL symbols; a TC32 build does not fetch those modules | `tc32/compat` gives them a type | Modules not fetched |
| The tlsr827x SoC series sets `TIMEOUT_64BIT=n`; ZMK's matrix driver uses `K_TIMEOUT_ABS_MS` | A board whose matrix uses ZMK's matrix driver sets `CONFIG_TIMEOUT_64BIT=y` in its defconfig (tc32-keyboards) | TC32 port default |
| ZMK's USB HID drops a report it cannot write (the host has not read the one before) and never sends it again. A computer waking from sleep can resume the bus before it reads the keyboard (macOS does, which is where it was seen): the key that woke it reached it as pressed and its release was dropped, so the key stayed held until pressed again | `app/src/usb_hid.c` marks the kind of report that could not be written and sends the newest one when the host takes the report in the endpoint | Hosts that resume before they read |
| ZMK's underglow converts every pixel from HSB to RGB in float, 20 times a second; the TC32 has no FPU, and on a TLSR8278 keyboard in the emulator, at the flash cache cost measured on a unit, the soft float left the watchdog's thread no CPU (three watchdog resets, then the boot guard went back) | `app/src/rgb_underglow.c` converts with integers: the same bytes to within 1 over every input | TC32 (no FPU) |
| ZMK's keymap lookup (`app/boards/post_boards_shields.cmake`) is called by a patch in ZMK's Zephyr fork, which zephyr-tc32 lacks | `build.sh` passes the board's keymap in `EXTRA_DTC_OVERLAY_FILE` | ZMK's Zephyr fork |

## Build

`tc32/scripts/build.sh` expects a workspace laid out as west lays out a ZMK workspace, with the toolchains next to it:

| Path | What |
|---|---|
| `<workspace>/tc32-keyboards/` | The keyboards: board directories, keymaps, the build wrapper (`TC32_BOARDS`) |
| `<workspace>/zmk/` | This repository |
| `<workspace>/zephyr/` | zephyr-tc32 (`west update` puts it there) |
| `<workspace>/toolchains/tc32-stage2/` | LLVM TC32: [modern-tc32/llvm-project](https://github.com/modern-tc32/llvm-project/releases/tag/20260606) release `20260606`, `tc32-llvm-toolchain-macos-arm64` (clang 23, triple `tc32-unknown-none-elf`); `toolchains/shim/llvm-readelf` links to its `llvm-readobj` |
| `<workspace>/toolchains/thumb-llvm/` | The clang for Thumb: a link to the install of [llvm-tc32](https://github.com/goyamamoto/llvm-tc32) ([below](#the-thumb-toolchain-llvm-tc32)), whose `bin/` holds clang, ld.lld and the llvm tools |
| `<workspace>/.venv-zephyr/` | Python venv with zephyr-tc32's `scripts/requirements-base.txt` |
| `<workspace>/build/` | The outputs |
| `tc32-devtools/` next to the workspace | `compiler/`: `tc32asm2thumb.py`, `thumb2tc32.py`, `image_check.py` |

`TC32_WORKSPACE`, `TC32_DEVTOOLS` and `TC32_BOARDS` (the tc32-keyboards checkout, by default `<workspace>/tc32-keyboards`) override the locations. A new workspace:

```sh
west init -m https://github.com/goyamamoto/zmk-tc32 --mf app/west.yml <workspace>
cd <workspace> && west update
```

Then, from the repository's folder (`cidoo_v75pro`, a board of tc32-keyboards, is `build.sh`'s default and stands for any of them):

```sh
tc32/scripts/build.sh cidoo_v75pro                  # LLVM TC32
THUMB=1 tc32/scripts/build.sh cidoo_v75pro          # clang for Thumb (toolchains/thumb-llvm) + thumb2tc32.py
DIRECT=1 tc32/scripts/build.sh cidoo_v75pro         # the direct path: llvm-tc32 -mcpu=tc32 + elf2bin.py
EXTRA_CONF=<file.conf> tc32/scripts/build.sh ...    # extra Kconfig fragments (;-separated)
```

The board's files come from `TC32_BOARDS`; tc32-keyboards' `build.sh` wraps this with each keyboard's fragments. The outputs are `zmk.elf`, `zmk.bin` and `zmk.ota.bin` (the image `tc32/scripts/telink_ota.py flash` installs) in `<workspace>/build/zmk_<board>/zephyr`, or in `$BUILD_DIR/zephyr`. The build string in the image's boot banner is always given to Zephyr (`-DBUILD_VERSION`): `v<major>.<minor>.<patchlevel>[-<extraversion>]-tc32` from the Zephyr tree's `VERSION` file (`v4.5.0-rc1-tc32`), or `$BUILD_VERSION`. So an image depends on the sources and the tools, not on the repositories' history or tags, and `build-info.json` records the value. With `THUMB=1`, clang builds ARMv4T Thumb and `thumb2tc32.py` writes `zmk.bin` in TC32 code; `image_check.py` then compares every byte of it with the ELF. The port's assembly goes through `tc32asm2thumb.py` (`TC32_THUMB_TOOLS`, which `build.sh` sets). Telink's own gcc is the reference compiler for the TC32 but cannot build Zephyr 4.4 or ZMK (no C11); tc32-devtools describes the compilers and their checks.

### The Thumb toolchain: llvm-tc32

The clang in `toolchains/thumb-llvm` is [llvm-tc32](https://github.com/goyamamoto/llvm-tc32), branch `tc32/23.1.2`: LLVM 23.1.2 with the changes for the TC32. tc32-keyboards' studio images (its `build.sh`'s default variant) set `CONFIG_TC32_POP_PC_RETURNS=y` (zephyr-tc32's `arch/tc32/Kconfig`): every C compile gets the Thumb-only target feature `noarm`, so a function that saved `lr` returns with `pop {..., pc}` instead of `pop {...}; pop {rN}; bx rN`. llvm-tc32 has that feature for ARMv4T; a mainstream clang ignores it without a message. So with this option the configuration first compiles a test function with the build's compiler (zephyr-tc32's `arch/tc32/CMakeLists.txt`), and with a mainstream clang it stops:

```
TC32_POP_PC_RETURNS: <workspace>/toolchains/thumb-llvm/bin/clang does not return with pop {..., pc} under -target-feature +noarm: it lacks the noarm feature (ignored without a message) or failed. Use a clang that has the feature, or set CONFIG_TC32_POP_PC_RETURNS=n.
```

Only the ARM target, clang and lld are needed. The command below leaves out LLVM's tests, examples, documentation and benchmarks, and `install-distribution` builds and installs only the tools listed in `LLVM_DISTRIBUTION_COMPONENTS` (the build folder takes about 1 GB, `<prefix>` about 210 MB):

```sh
git clone --depth 1 --branch tc32/23.1.2 https://github.com/goyamamoto/llvm-tc32
cmake -G Ninja -S llvm-tc32/llvm -B llvm-tc32-build \
  -DCMAKE_BUILD_TYPE=Release -DLLVM_ENABLE_ASSERTIONS=OFF \
  -DLLVM_ENABLE_PROJECTS="clang;lld" -DLLVM_TARGETS_TO_BUILD=ARM \
  -DLLVM_DEFAULT_TARGET_TRIPLE=thumbv4t-none-eabi \
  -DLLVM_INCLUDE_TESTS=OFF -DLLVM_INCLUDE_EXAMPLES=OFF \
  -DLLVM_INCLUDE_DOCS=OFF -DLLVM_INCLUDE_BENCHMARKS=OFF \
  -DCMAKE_INSTALL_PREFIX=<prefix> \
  -DLLVM_DISTRIBUTION_COMPONENTS="clang;clang-resource-headers;lld;llvm-ar;llvm-ranlib;llvm-nm;llvm-objcopy;llvm-strip;llvm-objdump;llvm-readobj;llvm-readelf;llvm-size;llvm-symbolizer;llvm-addr2line"
ninja -C llvm-tc32-build install-distribution
ln -s <prefix> <workspace>/toolchains/thumb-llvm
```

The build finds the compiler through `<workspace>/toolchains/thumb-llvm`: with `THUMB=1` (tc32-keyboards' `build.sh` sets it), `tc32/scripts/build.sh` passes that folder to Zephyr as `LLVM_TOOLCHAIN_PATH` and runs `llvm-readelf`, `llvm-nm` and `llvm-objdump` from its `bin/`. Zephyr preprocesses the linker scripts with clang without `--target`; `LLVM_DEFAULT_TARGET_TRIPLE` makes those commands Thumb's as well.

### The direct path: DIRECT=1

With `DIRECT=1` (tc32-keyboards' `build.sh` passes it through), llvm-tc32 writes TC32 code itself (`-mcpu=tc32`, zephyr-tc32's `TC32_DIRECT`). The assembly sources are their standard-syntax twins, `src/tlsr_spi_flash_io.ual.S` here; each build also compares each twin with its Telink-mnemonic file. `elf2bin.py` writes `zmk.bin` from the link without re-encoding. The checks are the same on both paths: `image_check.py`, `forms_check.py` (without `--thumb`), the flash supply trims, `boot_path_check.py` (which reads TC32 code back as Thumb), `rng_users_check.py`, `hot_slots.py` and the behavior IDs. `build-info.json` records `"direct"`. The two paths give byte-identical images; tc32-devtools' `path_diff.py` compares two images and names the symbol at any difference. The bytes `CONFIG_TLSR_HOT_TEXT_PAD` leaves after a board's hot text are `src/tlsr_hot_text_pad.S`, data of their own, so that the paths agree there too. `tc32/tests/zmk-tests-tc32/build.sh` takes `DIRECT=1` too.

With `CONFIG_TC32_POP_PC_RETURNS=n` in a Kconfig fragment (`EXTRA_CONF`), the feature and the check are off, and a mainstream clang builds the images (Homebrew's `llvm` and `lld`, linked into `toolchains/thumb-llvm/bin/`). The images are then larger, by 4,336 to 4,800 B on the three boards, and since the code moves, `hot_slots.py` may ask for another `CONFIG_TLSR_HOT_TEXT_PAD`. The `ble` and `wired` variants leave the option off.

### USB driver (`tc32/tests/usb-sim`)

`tc32/tests/usb-sim/run.sh` builds ZMK for `native_sim//zmk_test_mock` with the TLSR8278 `usb_dc` driver of `tc32/drivers/usb/device` and the USB OTA receiver of `tc32/`, and runs it in the Linux container of `tc32/tests/docker` (`python:3.12-slim-bookworm` with CMake from pip, since Zephyr 4.4 needs 3.28). It prints the run log without ZMK's debug lines (the full log is `<workspace>/build/usbsim.run.log`). It exits 0 on `RESULT: PASS` when no endpoint write found the endpoint busy: the legacy stack's `usb_write()` logs `Failed to write endpoint buffer` for each `-EAGAIN`, and `run.sh` fails on that line. The first run builds the image and needs network; the test itself runs with `--network none`. The image tag is a hash of `tc32/tests/docker/Dockerfile` and a copy of the Zephyr tree's `scripts/requirements-base.txt` that `tc32/tests/docker/image.sh` places next to it.

How it works:
- `src/tlsr_usb_model.c` stands in for the controller's registers:
  - EP0 is an 8-byte FIFO behind a post-incrementing data port, with a control register that arms each stage.
  - The data endpoints are 256 B of USB RAM with per-endpoint pointers and busy flags.
  - The interrupt status registers are write-one-to-clear, and the analog register port holds the DP pull-up and power bits.
  - The model follows the Telink SDK (`drivers/B87`, `application/usbstd/usb.c`).
  - Three switches cover what the SDK does not settle:
    - the EP0 pointer after an OUT packet: the byte count, 0 or 8;
    - whether events pend the interrupt lines, or only set status bits for the driver's poll;
    - the data toggle, checked on every IN packet taken: exactly one of DAT0/DAT1, alternating from DATA0 after a bus reset or SET_CONFIGURATION.
  - The flash simulator runs in RAM (`-flash_in_ram`), so every run starts from erased flash.
- `src/tlsr_usb_host.c` acts as the host. It raises the driver's interrupts with `posix_sw_set_pending_IRQ()`, the Zephyr legacy USB stack and ZMK's HID class answer through the driver, and the host checks the result:

| Step | Checked |
|---|---|
| Attach, bus reset | DP pull-up enabled |
| GET_DESCRIPTOR device (wLength 64) | 18 bytes, bMaxPacketSize0 8 |
| SET_ADDRESS | Status stage acked (the hardware applies the address) |
| GET_DESCRIPTOR configuration (9, then full) | 59 bytes over 8 packets; two HID interfaces: the keyboard (IN endpoint 1) and the OTA interface (IN endpoint 2), both with 64-byte packets |
| Product string | Equals `CONFIG_ZMK_KEYBOARD_NAME` over several packets |
| Manufacturer string, wLength 255 | 24 bytes, three full packets ended by a zero-length packet |
| Configuration descriptor, wLength 16 | Stops at 16 bytes on a full packet |
| A control read abandoned after one packet | The next SETUP works (device descriptor, 18 bytes) |
| SET_CONFIGURATION, GET_CONFIGURATION | 1 |
| HID report descriptor | Full length over 13 packets |
| SET_IDLE | Stalled by the legacy HID class without `CONFIG_USB_DEVICE_SOF`; the next transfer checks recovery |
| SET_REPORT output (LEDs) | OUT data stage with the EP0 pointer at the byte count, 8 and 0. ZMK's HID indicators read the value sent each time. The rest of the test runs with the pointer at 0 |
| Interrupt IN on endpoint 1 | The mock matrix taps A then B: A down, release, B down, release. IN completion alternates between the endpoint interrupt and the driver's 1 ms poll |
| OTA (`src/tlsr_usb_ota_host.c`) | Frames from `tc32/scripts/telink_ota.py` (generated at build time by `test/gen_ota_vectors.py`). Each goes as SET_REPORT (a 33-byte OUT data stage), and the response comes back on endpoint 2. Four cases: slot A to B, with a corrupted chunk (not acknowledged, sent again) and a repeated one; an image with a wrong CRC-32 (refused, no reboot, the running slot stays bootable); a chunk out of order (aborted); slot B to A. The native_sim flash simulator stands in for the flash, with writes that only clear bits. The test checks the slot contents and flag bytes |
| OTA, wrong running slot | Register 0x63e says slot B while the CPU runs slot A. Chunk 0 is refused with status 9, and slot B is not written |
| `&prev_fw` (the go-back key of `tc32/`) | The mock matrix holds the key bound to it for 1 s (nothing happens), then 3.5 s. Slot B, left by the OTA cases with its flag word cleared, becomes bootable, slot A's flag word is cleared, and the device reboots (a test hook). The boot guard (`CONFIG_TLSR_BOOT_GUARD`) runs in the same build |
| IN packet taken without an interrupt | With interrupts locked (no data interrupt, no poll), the host takes an IN packet on endpoint 2 and the next `usb_dc_ep_write()` returns 0. Each of the two packets is completed exactly once |
| Poll mode (no interrupt lines) | Bus reset and enumeration again, SET_REPORT, the OTA version command, and the mock matrix's last tap of A, all through the driver's 1 ms poll. The version answer carries the boot guard's clock (the test hook's 16 MHz), capture 244 and "ZC" |
| OTA update gate | In poll mode, slot B running, slot A holding an image that checks: chunk 0 of an update, after a start command and without one, gets status 13 and slot A stays as it was. After the unlock (0xff05) one chunk 0 is taken; it uses the unlock up, and an unlock ends after its window (300 ms in this test). An OTA test after the unlock leaves it in place. The version answers show the gate and the unlock |
| Data toggle | Every IN packet of the run (about 1,100): no wrong PID |

The test catches deliberate faults in the OTA receiver and the go-back key:
- Byte 8 of the new slot not held at 0xff while writing: the new slot is bootable before the end command.
- Old slot's flag word not cleared: both slots stay bootable.
- Image CRC-32 not checked: the bad image is installed and the device reboots.
- `&prev_fw` hold time not checked: the 1 s hold already goes back.
- The update gate's check left out: chunk 0 over slot A's image is taken without the unlock.
- The unlock not used up by chunk 0: the next chunk 0 is taken as well.
- The unlock's window not checked: chunk 0 after the window is taken.
- The gate applied when nothing checks in the other slot: the first update, into an empty slot B, gets status 13.

The test catches deliberate faults in the driver:
- An earlier driver (PID bits not set, EP0 OUT count from the pointer, interrupts only) fails the pointer-0 SET_REPORT and every OTA case after it. It also fails the poll-mode enumeration, and all 4 IN packets it checked have the wrong PID.
- OUT byte count ignored: the HID indicators check fails.
- EP0 pointer not reset between IN packets: the FIFO overflows on the second packet, so every IN transfer longer than 8 bytes fails and enumeration fails.
- 1 ms poll off: reports stop after the first packet taken without an interrupt.
- No completion in `usb_dc_ep_write()`: the write after a packet taken without an interrupt gets `-EAGAIN`, and the OTA cases log 6,050 `Failed to write endpoint buffer` lines.

Removing only one of the three EP0 pointer resets (after SETUP, on the data interrupt, on the first write of a packet) does not fail the test, because the other resets cover it.

The model covers the driver's side of the protocol only. It says nothing about timing, the analog/clock setup, or how the real controller behaves where the SDK is silent.
